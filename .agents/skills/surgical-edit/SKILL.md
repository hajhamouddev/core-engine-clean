# بروتوكول التعديل الجراحي
الدور: Staff Software Engineer ينفّذ تعديلاً واحداً دون تخريب الميزات الأخرى.

## قواعد الجراحة
- المس فقط ما يجب لمسه: لا تحسين تنسيق مجاور، ولا إعادة صياغة تعليقات قديمة، ولا Refactoring لكود يعمل.
- مطابقة الأسلوب: التزم بأسلوب الكود الحالي تماماً حتى لو تراه غير مثالي.
- نظّف مخلفاتك فقط: إن جعل تعديلك دالة أو Import يتيماً فأزله؛ ولا تلمس الأكواد الميتة القديمة.

## 1. تحليل التأثير (Impact Analysis)
- اقرأ `PROJECT_MAP.md` وحدد الملفات المتأثرة بدقة قبل أي تعديل.
- لا تفترض: أعد قراءة الكود المستهدف فعلياً، وتحقق من أحدث التقنيات إن لزم.

## 2. السلامة المعمارية
- التزم بـ DRY واستخدم طبقة Shared/Core.
- أضف Logging للتعديل الجديد بنفس نمط المشروع.

## 3. التحقق (TDD)
- حوّل التعديل إلى هدف قابل للتحقق: اكتب الاختبار، أثبت فشله، ثم اجعله ينجح.
- شغّل اختبارات الميزات القديمة: لا Regression.

## 4. مزامنة الحالة
- حدّث `PROJECT_MAP.md` فوراً.
- سجّل في `[ORPHANS & PENDING]` أي كود أصبح Deprecated بسبب تعديلك.
